# Categories to check

| Category | What to look for in the scan data |
|---|---|
| **Context pollution** | One session's `turns` cover unrelated topics (e.g. debugging a backend issue, then asking about CSS, then reviewing a PDF) — each unrelated pivot inflates context all subsequent turns pay for. Flag sessions that should have been split. |
| **Duplicated work** | Near-identical prompts recurring across sessions/turns (same question re-asked, same file re-explained) — signals missing memory or a stale mental model the user has to keep re-supplying. |
| **LLM used where a script would do** | Turns asking Claude to parse/reformat/compute/summarize structured data (logs, CSV, JSON, diffs) that a one-off script or existing CLI tool could produce deterministically and cheaper. Look for prompts like "count/list/extract/convert X from Y". |
| **MCP tools loaded but idle** | `mcpToolCalls` empty, or calls only appear very late in a long session. Caveat: the scanner only records tools that were *called*, not which MCP servers were *connected*, so this category can only ever catch "used late" — it cannot prove a loaded tool was never used, only that it wasn't used early. |
| **Skills without progressive disclosure** | Skill files that are long/monolithic (no separate reference files) get fully loaded on every invocation. Rule of thumb: keep the always-loaded `SKILL.md` under ~500 words, moving heavy reference material (tables, templates, exhaustive examples) into separate files pulled in on demand. If the `superpowers:writing-skills` skill is installed, it has the fuller rationale — consult it for extra detail, but the rule above is sufficient on its own. |
| **Oversized or over-specified prompts** | User turns that are very long (`length` in scan data) with excessive upfront detail the agent didn't need immediately — vs. a short prompt plus follow-up clarification, which is often cheaper because unused detail isn't loaded speculatively. |
| **Verbose/unsplit harness files** | CLAUDE.md/MEMORY.md that mixes always-relevant rules with rarely-needed detail (long troubleshooting runbooks, one-off project history) in a single file loaded every session — should be split with the rare parts referenced, not inlined. |
| **Wrong model for the task** | `modelsUsed` shows a high-capability model used for mechanical/repetitive turns, or vice versa. Caveat: `modelsUsed` is aggregated per session, not per turn, so you can see a session used two models but not which turns each covered — treat findings here as session-level signals, not proof about one specific turn, unless you cross-reference timestamps against `turns` by hand. |
| **Missed memory opportunities** | The user restates the same preference, correction, or project fact in multiple sessions — each restatement is tokens that a saved memory would have avoided. |
| **Redundant large reads/fetches** | The same file or URL fetched/read repeatedly across turns or sessions instead of cached/summarized once. |
